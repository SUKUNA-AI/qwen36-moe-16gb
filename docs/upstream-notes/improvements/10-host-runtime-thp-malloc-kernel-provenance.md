# [Feature] Host runtime: THP-backed private expert banks, glibc malloc tunables, and serving only source-bound prebuilt kernels

## Summary

Three host-side changes from our long-running single-GPU deployment, each small and independent:

1. **Expert banks as private anonymous memory with `MADV_HUGEPAGE`.** Upstream's `mmap.mmap(-1, n)` is `MAP_SHARED`
   (shmem). Where `shmem_enabled=never` (WSL2's default), the banks never get transparent huge pages.
2. **glibc malloc tunables in the launcher.** These stopped a host anon-memory growth that failed our 2-hour soak.
3. **Kernel provenance.** Prebuilt kernels are bound to a manifest of their recipe's source sha256. With
   `FREETOKEN_DISABLE_JIT=1`, an unbound or stale prebuilt is refused instead of silently loaded.

## Setup

- FreeToken 0.1.3 `cac247a8` plus our fork; `nvidia/Qwen3.6-35B-A3B-NVFP4` @ `1355db6a`, offloaded MoE
- RTX 5070 Ti 16 GB, WSL2 (`transparent_hugepage/shmem_enabled=never`; THP for anonymous memory via `madvise`), 28 cores

## Problem in upstream today

- **Banks.** `python/freetoken/moe/host_banks.py:112` allocates every pageable bank as
  `self._buf = mmap.mmap(-1, asize)`. Python maps `-1` as `MAP_SHARED|MAP_ANONYMOUS`, i.e. shmem. The repository
  contains no `MADV_HUGEPAGE` (only `MADV_SEQUENTIAL` in `checkpoint/ftw.py:284`). An earlier patch of ours called
  `madvise(MADV_HUGEPAGE)` on this mapping: under `shmem_enabled=never` that is a silent no-op. A 256 MiB test showed
  0 kB `ShmemPmdMapped`.
- **malloc.** The repository sets no `GLIBC_TUNABLES` / `MALLOC_ARENA_MAX`. With 28 cores, glibc may create up to
  224 arenas.
- **Kernel provenance (partly addressed).** `python/freetoken/kernel/utils.py:252-273` (`_load_prebuilt`) loads
  `cache_dir/<name>/<name>.so` by name only (`:262-266`). Since 0.1.3, main checks the kernel-cache wheel against the
  runtime: the release part must match, and the `g<sha>` build stamp too when both sides carry one
  (`_kernel_cache_version_ok`, `:193-207`). It still does not detect a `.so` whose `.cu`/`.cuh` sources, wrappers or
  flags changed under the same version, for example an edited source in a dev checkout with an unstamped cache.
  Related: #490 (a corrupted JIT cache crash-loops the engine).

## What we changed

- **THP banks** (`freetoken/python/freetoken/moe/host_banks.py`, `FREETOKEN_BANK_THP`, default on):
  - if `mmap.MADV_HUGEPAGE` exists, the bank is `mmap.mmap(-1, asize, flags=mmap.MAP_PRIVATE)` followed by
    `madvise(MADV_HUGEPAGE)` before first touch, so the fill faults in 2 MiB pages;
  - `FREETOKEN_BANK_THP=0` restores the shared 4 KiB mapping; bytes are unchanged;
  - this is safe because bank loads use threads and child processes are spawned (main also uses
    `mp.set_start_method("spawn")`, `server/launch.py:158`), so no fork shares the private pages.
- **malloc tunables** (launcher only, no code change):
  `GLIBC_TUNABLES=glibc.malloc.arena_max=2:glibc.malloc.mmap_threshold=1048576:glibc.malloc.trim_threshold=4194304`.
  We check it in the service process environment before and after each soak.
- **Kernel provenance** (`freetoken/python/freetoken/kernel/kernel_provenance.py`,
  `kernel/kernel_cache_manifest.json`, hooks in `kernel/utils.py`):
  - each `load_jit`/`load_aot` call builds a recipe: source files (CRLF folded to LF), the `csrc/include` tree,
    wrappers and flags;
  - a prebuilt `.so` is used only if the manifest binds that recipe digest to that `.so` sha256. A `.so` whose
    sha256 differs from the manifest raises;
  - without `FREETOKEN_DISABLE_JIT`, a refused prebuilt is JIT-built into a private directory keyed by the recipe
    digest (tvm-ffi's own cache keys inline sources by their `#include` lines, not by file contents);
  - with `FREETOKEN_DISABLE_JIT=1` (or `FREETOKEN_STRICT_PROVENANCE=1`) it raises `ProvenanceError` instead;
  - the manifest is generated by running the loaders in a capture mode that returns recipes instead of loading.
    Ours binds 83 modules. The module is stdlib-only, so release tooling can check it without CUDA.
  - ctypes libraries (our custom kernels) are separately pinned by sha256 and checked with an ABI probe.

## Measured impact

- **THP** (`docs/ARCHITECTURE.md` §4.1, `results/metrics/metrics.json`): the 256 MiB test went from 0 kB
  `ShmemPmdMapped` to 262144/262144 kB `AnonHugePages`. On the pcie-transfer microbenchmark, single copy-engine H2D
  from the registered banks went from 47.0 to 48.4-49.4 GB/s. In the release soak the bank shows up as anonymous
  memory, with shmem at 0.1 GiB. No end-to-end tok/s A/B was run for this switch alone.
- **malloc** (`docs/ARCHITECTURE.md` §4.2): before the change, the first 2-hour soak failed its memory gate with host
  anon +394 MB, growing in steps that lined up with fresh 64K/120K requests. After it: a 1-hour test grew +13.7 MB,
  baseline anon dropped by 192 MB, and the 2-hour soak grew +45-48 MB (gate threshold 268 MB). The arena-retention
  cause is a hypothesis we did not prove separately.
- **Provenance:** a correctness/operations change, not a speed change. A cold start with versus without JIT, or with
  versus without manifest checks, was not measured in isolation.

## Correctness evidence

- THP banks: same bytes, different page size. The released profiles keep the default (`FREETOKEN_BANK_THP` on), and
  their teacher-forced gates passed 125/125 logit checkpoints at max_abs 0.
- Provenance: every release run in our harness serves with `FREETOKEN_DISABLE_JIT=1`; the ctypes libraries are
  rehashed at release and at start. A dedicated negative test (an edited `.cu` refused) is not in the published
  evidence.

## Limitations / not measured

- THP was measured only on WSL2 with `enabled=madvise`. Bare-metal Linux with shmem THP enabled may already get huge
  pages from the shared mapping (not measured). `cudaHostRegister` on THP pages worked on our driver, but no other
  driver was tested.
- The malloc values were picked for one 28-core host and one serving pattern; other arena/threshold values were not
  swept.
- The manifest has to be regenerated whenever a kernel source changes, which adds a release step.

## Proposal

1. THP: a small PR to `host_banks.py` (private mapping plus `MADV_HUGEPAGE`, opt-out env). Is a default-on switch
   acceptable, or should it be opt-in?
2. malloc: document the tunables, or export them in `ft serve`/the service unit.
3. Provenance: we can upstream a recipe-digest check as an extension of `_load_prebuilt`. The kernel-cache wheel
   would ship the manifest it was built from, and `FREETOKEN_DISABLE_JIT=1` would refuse mismatches. Does this fit
   the current wheel versioning, or should the digest go into the cache layout instead?
