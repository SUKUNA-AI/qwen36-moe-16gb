# Лесенка main128: вклад каждого рычага

Сгенерировано 2026-10-16T03:43:06Z скриптами `scripts/ladder_*.py` из отчётов GPU-прогона. Бит-точность: teacher 125/125, max_abs 0.
A/B без профайлера: ротирующаяся матрица, 3 пары, прогрев 60 с, вывод 128 токенов. В ячейках: медиана (среднее; min–max; p95, p99; n) по парам; при n=3–5 перцентили — грубая оценка, она стремится к максимуму. Шаги кумулятивные: ступень = предыдущая + один рычаг.

## Главное

- **Каждая ступень бит-точна.** Все 13 конфигураций (L0–L11 и T3-only) прошли teacher-гейт: 125/125 контрольных точек, max_abs 0, все логиты побайтно равны, новых функциональных провалов нет. Эталон — свежий run-bound teacher-bf128, побайтно совпавший с закреплённым `logit-reference`.
- **Прирост даёт декод, а не время до первого токена.** На 16K декод вырос с 143 (L0) до 176 ток/с (L9, +23 %), на 120K — с 103 до 120 ток/с (+17 %). TTFT на 16K и 120K не меняется (1,32 с и 20,4 с), потому что prefill упирается в канал PCIe. TTFT коротких запросов падает с 0,39 до 0,20 с.
- **Вклад рычагов (декод 16K, ток/с, A/B 3 пары):** T1 +0,5, T2 −0,3 (шум), T3 +5,0, эмбеддинги на хосте +5,2, `memory_ratio` 0,85 +5,7, ядра S3 +10,8, C0 +1,4, C1 +2,1, D5 +2,6. D3b (L10) и D6 (L11) декод не улучшают: −7,2 и +4,5 к предыдущей ступени, итог ниже L9 по времени запроса, поэтому финальный кандидат — **L9 (`main-release-next-d5`)**.
- **Релизный A/B (5 пар, `compare-ab`): PASS** — время запроса baseline/кандидат: 64 токена ×1,37; 2K ×1,18; 4K ×1,18; 16K ×1,10; 120K ×1,015 (интервал 1,013–1,017); правки истории ×1,29–1,51. На 120K время запроса почти не меняется только потому, что 20 из 22 с — prefill, а декод ускорился на 17 %.
- **Установленный f1 и f1 на новом дереве одинаковы.** Один сеанс: декод 120K 102,8 против 103,5 ток/с. Расхождение с README (94,6) — условия той сессии, а не разница кода.
- **Память.** Слоты 3164 → 3729 (эмбеддинги на хосте) → 4611 (`memory_ratio` 0,85). У L6–L9 их 4603, а не 4611: самотесты ядер S3 при финализации весов оставляют в кеше аллокатора ≈14 МиБ, и они засчитываются как веса. Пик VRAM процесса ≤ 13,8 ГиБ при бюджете 15,6 ГиБ (1 ГиБ — Windows). Подкачки нет: shared-память Windows за 2-часовой soak +30 МиБ.
- **Гейты кандидата:** A, B, C, E — PASS; стадия D — внешний релизный A/B (см. `gates.json`, с хешами). Soak 2 ч: декод 64/4K/16K/64K/120K = 182/180/170/141/118 ток/с против 134/135/130/112/97 у f1-soak, TTFT не хуже на всех длинах.
- **long256 и 256K.** `long256-release` на новом дереве: teacher ровно 125/125, контекстные гейты 250K и boundary 262144 — PASS (`long256.json`). Полный кандидат на 256K (`long256-candidate.json`, только статистика): 250K TTFT 72,3 с, декод 76 ток/с (у long256 без рычагов 67).

## Оговорки

- Teacher для L0–L7 и T3-only снят на рантайме 686c6d0, для L8–L11 и long256 — на 19f8d1f/68605f5. Между ними S8 переложила код T3: L0–L2 им не затронуты, а квитанции L3–L7 и T3-only относятся к старому коду T3 (все более поздние ступени, где T3 включён, прошли на новом дереве). A/B снят на 19f8d1f для всех ступеней.
- Ступень L10: первый teacher-прогон оборвался на перезапуске юнита перед кейсом 120K (19 кейсов прошли чисто), повтор прошёл. Причина обрыва не найдена.
- В первом релизном A/B `compare-ab` дал INVALID из-за ошибки харнесса (строки `warmup_sustained`); исправлено, прогон повторён, учитывается только повтор.
- A/B лесенки — 3 пары (скрининг, не вердикт `compare-ab`); перцентили p95/p99 на n=3–5 — грубая оценка.
- Nsight Systems — диагностика под профайлером: время не является скоростью. Nsight Compute по модели не получен (см. конец).
